# 🎓 University Student & Academic Knowledge Assistant

An enterprise-style Retrieval-Augmented Generation (RAG) application for answering university student and academic questions from a controlled collection of university PDF documents.

The system uses:

- **Streamlit 1.64.0** for the web application
- **FAISS 1.15.1** for vector retrieval
- **BAAI/bge-m3** for semantic embeddings
- **Groq GPT-OSS 120B** (`openai/gpt-oss-120b`) for answer generation
- **JSON metadata** for document/page/chunk traceability

> **Important:** The original PDF documents are intentionally **not uploaded to GitHub** and are **not required at runtime**. The application uses the pre-built FAISS index and metadata generated by the Colab indexing pipeline.

# 3. Role of Each RAG File

## `index.faiss`

Contains the numerical vector representations of the indexed chunks.

It is the actual FAISS vector database.

The application performs:

```text
Question
   ↓
BGE-M3 vector
   ↓
FAISS similarity search
   ↓
Top-K vector IDs
```

---

## `metadata.json`

This is critical for source traceability.

Each vector has a corresponding metadata record.

The metadata contains information such as:

```json
{
  "source_file": "student_handbook.pdf",
  "source_path": "...",
  "page_number": 3,
  "total_pages": 6,
  "document_type": "PDF",
  "chunk_id": 17,
  "chunk_number_on_page": 2,
  "chunk_characters": 684,
  "embedding_model": "BAAI/bge-m3"
}
```

Therefore:

```text
FAISS vector #17
        ↓
metadata record #17
        ↓
student_handbook.pdf
        ↓
page 3
        ↓
specific text chunk
```

This allows the application to show:

```text
Source: student_handbook.pdf
Page: 3
Chunk ID: 17
Similarity: 0.8124
```

and the LLM can cite:

```text
[student_handbook.pdf, p. 3]
```

---

## `embedding_config.json`

Stores the configuration required to reproduce query embeddings consistently.

Example:

```json
{
  "embedding_model": "BAAI/bge-m3",
  "embedding_dimension": 1024,
  "normalize_embeddings": true,
  "similarity": "cosine",
  "faiss_index_type": "IndexFlatIP",
  "chunk_size": 700,
  "chunk_overlap": 120
}
```

The application checks this configuration before retrieval.

---

## `document_manifest.json`

Stores document-level information and SHA-256 hashes.

Example:

```json
{
  "file_name": "student_handbook.pdf",
  "file_size_bytes": 1234567,
  "sha256": "...",
  "pages": 6,
  "document_type": "PDF"
}
```

This allows you to identify exactly which source document was used when the index was created.

# 5. Source Traceability

Source traceability is implemented at multiple levels.

### Level 1 — Document

```text
source_file
```

Example:

```text
student_handbook.pdf
```

### Level 2 — Page

```text
page_number
```

Example:

```text
Page 4
```

### Level 3 — Chunk

```text
chunk_id
chunk_number_on_page
```

### Level 4 — Retrieval

```text
similarity score
FAISS vector index
```

### Level 5 — LLM answer

The model is instructed to cite claims using:

```text
[Document Name, p. X]
```

Example:

```text
Students must satisfy the stated academic requirements
before proceeding to the next stage [student_handbook.pdf, p. 4].
```

# 6. Groq Configuration

The application uses the official Groq Python SDK.

The API key is **never stored in GitHub**.

Set:

```text
GROQ_API_KEY
```

as a Streamlit Cloud secret.

The application uses:

```python
from groq import Groq

client = Groq(
    api_key=os.environ.get("GROQ_API_KEY"),
)
```

and:

```python
chat_completion = client.chat.completions.create(
    messages=[
        {
            "role": "system",
            "content": SYSTEM_PROMPT,
        },
        {
            "role": "user",
            "content": user_prompt,
        },
    ],
    model="openai/gpt-oss-120b",
)
```

# 10. Updating the Knowledge Base

When a university document changes:

```text
New PDF
   ↓
Run Colab indexing notebook
   ↓
Create new embeddings
   ↓
Create new FAISS index
   ↓
Create new metadata
   ↓
Replace rag_index/
   ↓
Git commit
   ↓
Git push
   ↓
Streamlit redeploy
```

Do not manually edit `index.faiss`.

The FAISS index and metadata must always come from the same indexing run.

---

# 11. Important Embedding Rule

The production application uses:

```text
BAAI/bge-m3
```

because the existing FAISS index was created with BGE-M3.

Do **not** change the query embedding model without rebuilding the FAISS index.

For example, this would be incorrect:

```text
Indexed with BGE-M3
        ↓
Query embedded with MiniLM
        ↓
FAISS search
```

The embedding spaces would not match.

Correct:

```text
Document chunks → BGE-M3 → FAISS

User query      → BGE-M3 → FAISS
```

# 14. Design Principle

The system intentionally separates:

### Offline indexing

```text
PDFs
 ↓
Extraction
 ↓
Cleaning
 ↓
Chunking
 ↓
BGE-M3
 ↓
FAISS + Metadata
```

from:

### Online application

```text
User
 ↓
Question
 ↓
BGE-M3
 ↓
FAISS
 ↓
Metadata
 ↓
Groq
 ↓
Answer + Sources
```

This means the expensive document processing happens only when the knowledge base is updated.

The deployed application only performs query embedding, vector retrieval, and LLM generation.
